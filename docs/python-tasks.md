# 11. Обязательная работа с Python и PostgreSQL

План: ещё 2,5–3,5 часа после SQL. Ты пишешь функции в database.py, find_reader.py, library_queries.py и transactions.py. main.py уже содержит меню и вызовы всех функций. Обе операции выдачи и возврата обязательно реализуй через Python: выполнения тех же действий вручную в pgAdmin недостаточно.

## Подготовка — 20 минут

После SQL-заданий база library_extended содержит 12 читателей и 17 выдач. Выдача 200 закрыта, copies книги 10 равно 3, copies книги 80 равно 5. Исходные CSV повторно не загружай.

1. Установи зависимости: `python -m pip install -r requirements.txt`.
2. Реализуй database.connect(): прочитай PGHOST, PGPORT, PGDATABASE и PGUSER из окружения с умолчаниями localhost, 5432, library_extended и postgres. PGPORT преобразуй в int.
3. Запроси пароль через getpass.getpass и передай его в psycopg.connect. Возвращай новое открытое соединение. Используй стандартный autocommit=False.
4. В остальных функциях используй эту функцию подключения. Не дублируй настройки и запрос пароля. Каждый вызов операции открывает своё соединение и закрывает его при выходе из with.
5. Запускай `python main.py` из терминала. Все .py-файлы лежат рядом. Для другой базы задай PGDATABASE. Пароль и действительную строку подключения не сохраняй в Git.

## Чтение данных — 30 минут

Реализуй три функции. Все передаваемые значения подставляй через параметры Psycopg. Функции возвращают данные, а main.py их печатает.

1. `find_reader(reader_id)` возвращает name или None. Для id=1 и id=11 результатом будут имена двух разных читателей «Алиса». Для id=999 — None. Поиск идёт по первичному ключу, не по имени.
2. `available_books(min_copies=1)` возвращает список кортежей `(id, title, copies, price)`, где copies >= min_copies. Сортировка по copies DESC, затем id ASC. min_copies — целое число не меньше 1, иначе ValueError до открытия соединения. Если подходящих книг нет, верни []. Значение price оставь Decimal, как его вернул драйвер.
3. `reader_loans(reader_id)` через JOIN возвращает текущие выдачи: список `(loan_id, title, due_date)`. Только returned=FALSE, порядок по due_date, затем loans.id. Дату оставь datetime.date. Для читателя без текущих выдач или несуществующего читателя верни [].

Пустой результат — нормальный ответ. Ошибка SQL или подключения не должна превращаться в None или []. В main.py уже есть обработчик ошибок PostgreSQL.

## Добавление читателя — 20 минут

Реализуй `add_reader(reader_id, name, email, city, registered_on)`:

- Добавь активного читателя параметризованным INSERT, registered_on — datetime.date.
- Пустой email из меню уже преобразуется в None.
- Используй with для соединения: успешная операция подтверждается, ошибка откатывается.
- После успешного завершения верни reader_id. Ошибки повторного id или email не скрывай и не заменяй обновлением существующей строки.

Для ручной проверки используй читателя id=90, имя «Учебный читатель», email=NULL, город «Тула», registered_on=2026-06-01. Этот id свободен после SQL-заданий. После добавления readers содержит 13 строк. Повторное добавление id=90 должно завершиться ошибкой и не менять строку.

## Транзакция 1: выдача книги — 40 минут

Реализуй `issue_book(loan_id, reader_id, book_id, loan_date, due_date, *, fail_after_update=False)`.

1. Проверь порядок дат: due_date не раньше loan_date. Иначе ValueError без изменения базы.
2. Открой **одно соединение**. Внутри одного блока with проверь, что читатель существует и active=TRUE. Иначе ValueError.
3. Уменьши copies только для нужной книги и только при copies>0. Используй условие в самом UPDATE, а не отдельный SELECT с последующим безусловным уменьшением.
4. Проверь cursor.rowcount. Если обновлено 0 строк, подними ValueError: книга не найдена или нет экземпляров. Выдачу в этом случае не добавляй.
5. Если fail_after_update=True, подними RuntimeError с текстом «Учебная ошибка выдачи» сразу после уменьшения copies, до INSERT. Исключение должно выйти из with.
6. Добавь строку loans с переданными id и датами, returned=FALSE, returned_date=NULL. Повтор id выдачи должен остаться обычной ошибкой PostgreSQL.
7. При успехе обе записи изменений подтверждаются вместе. Верни loan_id после завершения with.

Проверки чтения и оба изменения должны использовать одно соединение. Нельзя вызывать commit между UPDATE и INSERT, включать autocommit или подавлять исключение внутри with. В этом учебном сценарии проверка active описывает состояние на момент чтения; изменение статуса читателя другой сессией одновременно с выдачей отдельно не моделируем.

## Транзакция 2: возврат книги — 35 минут

Реализуй `return_book(loan_id, returned_on, *, fail_after_update=False)`.

1. Открой одно соединение и один блок with для всей операции.
2. Одним UPDATE закрой только выдачу с нужным id и returned=FALSE. Одновременно установи returned=TRUE и returned_date=returned_on.
3. Добавь `RETURNING book_id`, чтобы получить id книги из реально изменённой строки. Если fetchone() вернул None, подними ValueError: выдача не найдена или уже закрыта. copies менять нельзя.
4. Если fail_after_update=True, подними RuntimeError «Учебная ошибка возврата» после закрытия выдачи, до увеличения copies. Исключение должно выйти из with.
5. Увеличь copies только найденной книги на 1 в том же соединении.
6. Успешный выход подтверждает оба изменения; верни book_id. При ошибке CHECK даты или второй команды первая часть также должна откатиться.

Такой порядок предотвращает повторное увеличение copies при втором возврате той же выдачи: второй UPDATE не изменит уже закрытую строку. SQL RETURNING — небольшое дополнение к уроку, смотри подсказку в конце.

## Подсказки по API

`cursor.rowcount` — число строк, затронутых UPDATE. Это свойство курсора, который вернул con.execute().

`UPDATE ... RETURNING поле` возвращает значение из изменённой строки. После него можно вызвать fetchone(); если строк не изменено, результат None. Пример синтаксиса на условной таблице: `UPDATE example SET enabled = FALSE WHERE id = %s RETURNING id`. Реальные запросы к библиотеке напиши самостоятельно.

В Psycopg 3 контекст соединения подтверждает транзакцию при обычном выходе, откатывает при исключении и закрывает соединение. Обычный SELECT тоже может начать транзакцию; в функциях не оставляй соединения открытыми.

Документация: [Psycopg — транзакции](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [параметры](https://www.psycopg.org/psycopg3/docs/basic/params.html), [PostgreSQL — RETURNING](https://www.postgresql.org/docs/18/dml-returning.html).
